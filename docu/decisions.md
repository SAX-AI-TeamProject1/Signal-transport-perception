# 설계 결정 기록 (ADR)

이 문서는 YOLO 기반 장애물 인식 파이프라인을 설계하며 대화로 확정한 결정들을 배경/결정/근거 순서로 기록한다. 각 항목은 이후 결정으로 뒤집힐 수 있으며, 뒤집힌 경우 새 ADR을 추가하고 이전 항목은 남겨둔다(왜 그렇게 안 했는지의 기록도 가치가 있음).

Last updated: 2026-07-31

## ADR-001 태스크 유형: Image Classification이 아닌 Object Detection

- **배경**: 사람/사물을 구분해 정지·회피를 판단하는 게 목적이고, 이후 물체 크기 추정(라이다 거리와 결합)에 바운딩박스 좌표가 필요함.
- **결정**: `yolov8n-cls`가 아니라 detect 계열(`yolov8n.pt` 등)을 사용한다.
- **근거**: 한 프레임에 여러 물체가 섞여 있어도 개별로 위치+클래스를 잡아낼 수 있고, 바운딩박스 크기가 이후 크기 기반 판단(ADR-004)의 입력이 된다.

## ADR-002 학습 데이터 소스: COCO val2017 서브셋

- **배경**: `data/`가 비어있는 상태로 시작. 직접 촬영은 하지 않기로 하고, 공개 데이터셋에서 약 1,000장 규모로 시작하기로 함.
- **결정**: COCO val2017(5,000장) 중 라벨이 존재하는 이미지에서 무작위 1,000장을 샘플링(train 800 / val 200)한다. 이미지는 공식 zip(`images.cocodataset.org/zips/val2017.zip`), 라벨은 ultralytics가 배포하는 사전 변환 YOLO 포맷 zip(`coco2017labels.zip`)을 사용한다.
- **근거**: YOLO 사전학습 가중치가 이미 COCO로 학습되어 있어 클래스 정의·라벨 포맷이 그대로 들어맞고, 별도 포맷 변환 스크립트가 필요 없다. 전체 COCO(train+val, 약 20GB)보다 훨씬 가볍다.
- **트레이드오프**: COCO는 일반 웹/일상 사진이라 실제 로봇 카메라 환경(근거리, 실내, 특정 배경/조명)과 도메인 차이가 있다. 파이프라인이 완성된 뒤, 필요하면 실촬영 데이터를 보강하기로 함(미착수).

## ADR-003 클래스 구성: COCO 80클래스 그대로 사용 (재매핑하지 않음)

- **배경**: 논의 중 "사람/차량/사물"처럼 3~4개로 압축하는 안을 검토했으나(공장·일상 물품을 폭넓게 인식하고 싶다는 요구와 충돌), 최종적으로 "최대한 다양한 물체 종류를 인식"하는 것이 목표로 재확인됨.
- **결정**: 라벨 클래스 ID를 재매핑하지 않고 COCO 원본 80클래스(`0: person` ~ `79: toothbrush`)를 그대로 학습한다.
- **근거**: 행동 판단(정지/회피)은 모델이 예측한 클래스명을 별도 로직(ADR-004)에서 룩업하는 방식으로 처리하므로, 모델 자체는 인식 가능한 종류를 최대화하는 쪽이 유리하다. 재매핑 파이프라인의 복잡도도 없앨 수 있다.
- **기각된 대안**: person/vehicle/object 3~4클래스 압축. 재학습 라벨 가공이 추가로 필요하고, 인식 다양성이 줄어들며, "물체별로 통과 가능 여부가 다르다"는 요구사항을 클래스 자체에 하드코딩하면 오히려 예외 처리가 경직된다는 문제가 있었음(ADR-004에서 다른 방식으로 해결).

## ADR-004 행동 판단 로직: 클래스 기반 룩업 + 크기 기반 판단, 라이다 거리 연동

- **배경**: 사람=정지, 차량=회피는 명확하지만, 그 외 물체(페트병, 상자 등)는 종류보다 크기·무게에 따라 통과 가능 여부가 달라야 한다는 요구가 있었음. 다만 카메라 바운딩박스 픽셀 크기만으로는 실제 물리적 크기를 알 수 없다(같은 물체도 거리에 따라 프레임 내 크기가 달라짐). 무게는 어떤 센서로도 직접 측정할 수 없음.
- **결정**:
  - `person` 클래스 예측 → **STOP**, 라이다가 감지한 거리 이내로 들어왔을 때 트리거.
  - 차량 계열 클래스(`car, truck, bus, motorcycle, bicycle, train`) 예측 → **AVOID**, 마찬가지로 라이다 감지 거리 기준으로 트리거.
  - 그 외 클래스 → 바운딩박스 크기와 라이다 거리를 결합해 추정한 실제 크기를 기준으로 통과/회피를 판단.
  - 무게는 측정하지 않고, 클래스 기반 휴리스틱 가정으로 대체한다(예: 페트병류는 가볍다고 가정).
- **근거**: 라이다는 거리·형상은 측정할 수 있어도 질량은 측정할 수 없으므로, 무게는 애초에 센서로 풀 수 있는 문제가 아니다. 클래스 지식 기반 근사가 현실적인 최선.
- **미해결**: 크기의 "작다/크다" 임계값과, 바운딩박스+거리로 실제 크기를 계산하는 정확한 공식은 아직 정하지 않음. 오분류·낮은 confidence 상황에서 기본값을 안전한 쪽(회피)으로 떨어뜨리는 fail-safe 처리도 논의는 했으나 최종 반영 여부 미확정.

## ADR-005 레포 간 책임 경계

- **배경**: `env/AGENT.md`에 이미 문서화된 경계 — 라이다 충돌 감지와 로봇 모션 제어는 Signal-Simulation(Gazebo + ROS 2)이 담당하고, 카메라 기반 이미지 처리는 이 레포가 담당한다.
- **결정**: ADR-004의 행동 판단 로직(STOP/AVOID/크기 판단)까지는 이 레포 안에서 구현한다. 최종적으로는 Signal-Simulation의 로봇 제어 로직이 소비할 수 있도록 결과를 ROS 2 토픽/메시지로 넘기는 형태를 지향한다.
- **미해결**: 정확한 토픽 이름·메시지 타입·좌표계는 여전히 미정 (`env/AGENT.md`에도 명시된 기존 미결정 사항).

## ADR-006 코드/데이터 배치 컨벤션

- **배경**: 프로젝트 전반이 리포 루트에서 스크립트를 실행하는 컨벤션을 따르고 있음(`tools/update_date_header.py`, VS Code 태스크의 `cwd`가 모두 `${workspaceFolder}`).
- **결정**: 모든 소스코드는 `src/` 아래에 작성하고, 항상 리포 루트에서 `python src/xxx.py` 형태로 실행한다. `data/dataset/dataset.yaml`의 `path`도 리포 루트 기준 상대경로(`data/dataset`)를 사용한다.

## ADR-007 학습 데이터 소스: 실사진(COCO/Roboflow) → Gazebo 자체 렌더링

- **배경**: 로봇은 Gazebo(navi_factory 월드, AWS RoboMaker 창고 에셋)에서만 시뮬레이션되는데, 지금까지 학습 데이터는 전부 실사진(COCO) 또는 실사진 기반 공개 데이터셋(Roboflow warehouse-management)이었다. 처음엔 이 갭을 Blender로 에셋을 오프라인 렌더링해서 메우려 했으나(`render_gazebo_assets.py`), 실제 Gazebo 화면으로 검증해보니 Blender로 학습한 모델의 confidence가 0.98대에서 0.27~0.46대로 떨어지고 중복/헐렁한 박스가 발생했다 — Blender와 Gazebo 렌더러(조명·텍스처 처리)가 서로 달라 도메인 갭이 그대로 남아있었기 때문. 또한 Blender 5.x의 Collada 임포터 제거, assimp 변환 중 재질 투과율 오작동, 텍스처 상대경로 깨짐 등 렌더러 자체와 무관한 변환 버그도 여러 번 발생했다.
- **결정**: 학습 이미지를 Gazebo 자체 카메라 센서로 직접 캡처한다(`capture_gazebo_dataset.py`). `worlds/navi_factory/navi_factory.sdf`(실제 로봇 시뮬레이션에 쓰이는 월드)는 절대 건드리지 않고, 클래스마다 별도의 빈 월드를 이 레포의 `data/raw/gazebo_capture/_worlds/`에 즉석에서 생성해 스폰·촬영·종료한다. 카메라는 고정하고 대상 오브젝트의 자체 yaw 회전 + 카메라 정면축 위 거리 이동으로 스윕한다(카메라가 물체 주위를 도는 것과 기하학적으로 동일).
- **근거**: 실제 배포 시 로봇이 보는 렌더러·조명을 그대로 학습에 쓰는 게 가장 근본적인 도메인 일치 방법이고, DAE를 변환 없이 그대로 읽으므로 Blender 파이프라인에서 겪은 변환 버그 자체가 발생할 여지가 없다.
- **한계**: 라벨(바운딩박스)은 각 메시의 Blender 측정치(半-extent)를 기반으로 투영 계산하는데, Blender 임포트본과 Gazebo 네이티브 렌더 사이에 치수가 미세하게 달라(예: PalletJackB_01 손잡이 끝부분이 살짝 박스 밖으로 나감) 1.2배 여유값(padding)으로 보정했다. 일부 클래스(예: ClutteringA_01처럼 비정형 박스 더미)는 근거리·특정 각도에서 라벨이 다소 느슨하거나 물체 일부를 놓칠 수 있음 — 지금은 허용 가능한 수준으로 판단하고 넘어감, 필요해지면 재검토.

## ADR-008 클래스 구성 재정리: 에셋 단위(6종) → 의미 단위(4종)

- **배경**: ADR-007 캡처 스크립트가 처음엔 `PalletJackB_01, Bucket_01, ClutteringA_01, ClutteringC_01, ClutteringD_01, TrashCanC_01`처럼 AWS RoboMaker 에셋 파일명(버전 접미사 포함)을 그대로 클래스로 썼다. 그런데 `ClutteringA/C/D_01`는 전부 "잡동사니 더미"라는 같은 개념이고, ADR-004의 행동 판단 로직상 이런 "그 외" 오브젝트는 어차피 크기 기반으로 동일하게 처리되므로 세 클래스로 쪼갤 이유가 없다는 지적이 있었음.
- **결정**: 물리적으로 서로 다른 3D 메시(캡처 시엔 하나씩 따로 스폰해야 함)와, 라벨에 실제로 쓰는 의미 클래스를 분리한다. `capture_gazebo_dataset.py`의 `MESH_GEOMETRY`(메시별 치수)와 `SEMANTIC_CLASSES`(최종 4클래스: `PalletJack, Bucket, Cluttering, TrashCan`)로 나눠서, 여러 메시가 하나의 class_id로 묶여 라벨링되게 했다. `prepare_dataset.py`도 폴더명이 아니라 라벨 파일에 적힌 class_id로 그룹핑하도록 수정.
- **근거**: 클래스가 적어질수록 클래스당 학습 데이터(형태 다양성)가 늘어나고(`Cluttering`은 이제 324장, 메시 3종의 다양한 형태를 봄), 이 프로젝트의 행동 판단 로직이 애초에 요구하지 않는 세밀함을 클래스 taxonomy에 넣지 않게 된다. ADR-003의 "COCO 80클래스를 그대로 쓴다"는 결정과는 배경이 다르다 — 거긴 "인식 다양성 최대화"가 목적이었고, 여긴 "에셋 파일명이라는 구현 디테일이 클래스로 새어나가지 않게" 하는 정리다.

## ADR-009 학습 실행 위치: 로컬(MPS) → Kaggle(GPU)

- **배경**: 로컬 M4 Mac(MPS)으로 648장/50epoch 학습이 약 32분 걸려 반복 실험하기엔 느리다는 피드백이 있었음. 이미 이 프로젝트용 Kaggle 노트북(`heojaeseong/yolo-percep`)이 있었는데, 원래는 Roboflow에서 직접 데이터를 받아 학습하는 구조였음(ADR-002의 Roboflow 단계 유물).
- **결정**: `data/dataset/`을 Kaggle Dataset(`heojaeseong/yolo-gazebo-capture`)으로 업로드하고, 노트북에서 Roboflow 다운로드 로직을 제거해 이 데이터셋을 직접 참조하도록 교체. T4 GPU로 같은 50epoch가 약 7분에 끝남.
- **주의사항**: `prepare_dataset.py`가 생성하는 `data.yaml`의 `path`는 로컬 절대경로라서, Kaggle에 그대로 올리면 컨테이너 안에서 그 경로를 못 찾아 실패한다(1차 시도 때 실제로 겪음) — 노트북 쪽에서 `path`를 `/kaggle/input/<dataset>`으로 재작성하는 셀을 앞에 추가해서 해결. 데이터셋을 다른 환경에 옮길 때마다 반복될 수 있는 문제라 기억해둘 것.
- **한계**: Kaggle 학습은 사람이 노트북을 열어 수동으로 트리거하는 방식은 아니고 `kaggle kernels push`로 트리거하지만, 여전히 로컬 `.venv`가 아니라 Kaggle 계정/API 인증이 필요하다 — 팀원이 재현하려면 각자 Kaggle 계정과 `kaggle` CLI 인증이 필요함.
- **기본 경로 확정**: 실제 학습(정식 50epoch)은 **Kaggle을 기본으로** 한다 — `prepare_dataset.py`가 분할 후 자동으로 데이터셋을 업로드하도록 만들어놨으니 로컬보다 손이 더 안 간다. `src/train.py`(로컬 MPS)는 인터넷이 없거나 코드 변경 자체를 1~2epoch로 빠르게 스모크테스트할 때만 쓴다.

## ADR-010 라벨 계산 방식: 수동 half-extent 투영 → gz-sim `boundingbox_camera` 자동 라벨링

- **배경**: ADR-007에서 navi_factory 월드에 person/vehicle 모델이 없다고 기록했으나, 실제로는 Signal-Simulation 쪽에 `StandingPerson/WalkingPerson/CasualFemale`(사람), `Forklift`(차량)가 이미 배치돼 있어 그 미해결 항목은 해소된 상태였다. 다만 이 레포의 라벨링 방식(`MESH_GEOMETRY`)은 각 메시의 half-extent를 Blender로 측정해 하드코딩한 뒤 카메라 intrinsics로 삼각함수 투영하는 방식이었는데, 이 프로젝트는 Blender를 쓰지 않기로 한 상태라 새 클래스마다 이 수치를 채울 방법이 없었다.
- **결정**: gz-sim(Harmonic, 8.14) 자체에 있는 `boundingbox_camera` 센서 + `gz-sim-label-system` 플러그인으로 완전히 대체한다. 각 RGB `camera` 센서와 동일한 pose에 `box_type=visible_2d`인 `boundingbox_camera`를 짝지어 띄우고, 스폰하는 대상 오브젝트(`<include>` 또는 수동 구성한 `<model>`)에 `gz-sim-label-system` 플러그인으로 `class_id`를 라벨로 부여한다. 렌더러가 직접 계산한 픽셀 단위 `AnnotatedAxisAligned2DBox_V`를 그대로 YOLO 정규화 좌표로 변환한다 — `yolo_label()`의 삼각함수 투영, `half_x/half_y/half_z`, `BOX_PADDING`(1.2배 여유값)이 전부 없어졌다.
- **근거**: 렌더러가 실제로 그린 실루엣에서 박스를 뽑으므로 Blender 임포트본과 Gazebo 네이티브 렌더 사이의 치수 오차(ADR-007의 한계였던 손잡이 잘림 등)가 원천적으로 발생하지 않고, 패딩 보정도 불필요해졌다. 새 클래스를 추가할 때 필요한 입력이 "메시 경로 + (선택) 카메라 거리 스케일용 대략적 반지름"뿐이라 측정 도구(Blender) 의존이 완전히 사라진다.
- **자체 model.sdf가 없는 메시(Person 3종, Forklift)**: `navi_factory.sdf`가 이 오브젝트들을 배치할 때 쓰는 `<visual>` 구성(mesh 경로, visual pose)을 그대로 재사용해 `capture_gazebo_dataset.py`에서 수동으로 `<model>`을 구성한다(`RAW_MESH_MESHES`). navi_factory.sdf에서 이들은 전부 `<static>true</static>` 배경 소품이라 물리 충돌이 필요 없어 별도 collision은 만들지 않았고, 중심 높이(`center_z`)는 항상 0(메시 원점이 이미 지면 높이)이다. 카메라 거리 스케일용 반지름은 navi_factory.sdf에 이미 작성된 콜리전 치수(Person 0.5x0.35x1.8m, Forklift 2.4x1.4x2.06m)의 bounding-sphere 반지름을 계산해서 얻었다 — 새로 측정한 값이 아니라 Signal-Simulation이 이미 갖고 있던 값을 재사용한 것.
- **카메라 거리/높이도 실시간 캘리브레이션으로 대체**: 처음엔 라벨 계산만 자동화하고 카메라 거리 스케일용 "반지름"과 지면 위 "중심 높이"는 여전히 메시별 상수로 남겨뒀는데(4개 기존 클래스는 옛 Blender 시절 값을 그대로 재사용, 신규 2개는 navi_factory.sdf의 콜리전 치수에서 계산), 이 역시 "왜 여전히 메시마다 숫자를 채워 넣냐"는 지적을 받고 완전히 없앴다. `calibrate_target()`이 캡처 시작 직전 `boundingbox_camera` 피드백만 보면서 (1) 물체가 기준 카메라 프레임에 들어올 때까지 거리를 좁히고 (2) 박스가 세로 중앙에 오도록 높이를 원근 비례로 보정하고 (3) 박스 세로 길이가 목표 프레임 비율(`TARGET_FILL`)이 되도록 거리를 다시 맞추는 짧은 피드백 루프를 돌려 실측한다. 이제 새 클래스를 추가할 때 필요한 정보는 "어떤 메시를 스폰할지"뿐이다.
- **검증**: 기존 4클래스 중 `TrashCanC_01`/`Bucket_01`로 회귀 캡처를 돌려 새 방식이 기존과 동등하게(오히려 더 타이트하게) 동작함을 확인했고, 신규 `StandingPerson`/`Forklift`도 각각 캡처해 픽셀 단위로 딱 맞는 박스가 나옴을 시각적으로 확인했다. (첫 구현에서 높이 보정 루프의 부호가 반대로 돼 있어 물체가 하늘로 발산하는 버그가 있었음 — 수정 후 재검증)
- **범위 밖(보류)**: `OGV`(차량 후보)는 자체 `model.sdf`에 collision이 아예 없고 인스턴스마다 스케일도 다르게 오버라이드돼 있어(6,6,6 vs 9,9,9) 이번 작업에서는 제외했다 — Vehicle 클래스는 우선 `Forklift`만으로 시작.

## ADR-011 트랙(차선) 추종: 색상 기반 센터라인 인식 + 라우팅은 Signal-Simulation 담당

- **배경**: navi_factory 월드에는 로봇이 시각적으로 따라가야 할 주황색 대시라인 트랙(`track_*`
  모델들)이 깔려 있고, 스크린샷으로 확인해보니 직선 구간뿐 아니라 분기점·반환점·목표지점(원형
  패드, 콘+원형 마커 등 형태가 다른 마커)까지 있는 실제 라우팅 네트워크였다. 이건 지금까지의
  라이다-트리거 YOLO 장애물 분류(ADR-001~010)와는 별개로, 카메라 프레임을 상시 보면서 도는
  "차선 유지" 문제다.
- **결정**:
  - **인식 방식**: YOLO 대신 HSV 색상 threshold 기반 센터라인 검출을 쓴다. `track_*` 마커는
    단일 주황색(`ambient/diffuse 1 0.35 0 1`)이라 학습 데이터 없이도 안정적으로 뽑히고,
    바운딩박스 여러 개보다 코너에서 부드럽게 이어지는 곡선을 얻기에 더 적합하다.
  - **라우팅 책임 분리**: 분기점에서 어느 쪽으로 갈지, 언제 반환/정지할지 같은 상위 판단은 이
    레포가 하지 않는다. Signal-Simulation이 이미 웨이포인트 순서(경로)를 알고 있다고 보고,
    이 레포(`src/track_follow.py`)는 "지금 눈앞 트랙에 얼마나 치우쳐 있는지(offset)·얼마나
    꺾이는지(curvature)"만 인식해서 넘긴다 — 기존 레포 간 경계(ADR-005: 모션 제어는
    Signal-Simulation)를 그대로 확장한 것.
  - **여러 차선/차량 혼동 방지**: 화면에 여러 트랙 분기가 동시에 보여도, connected-component
    중 로봇 바로 앞(화면 하단 중앙)에 맞닿은 것 하나만 "내 트랙"으로 선택한다(`select_own_track`).
    다른 차량(Vehicle/Person)이 트랙을 가리거나 트랙과 색이 비슷해 오검출을 일으키는 것은,
    이 레포가 이미 갖고 있는 YOLO 탐지 결과(바운딩박스)를 그대로 마스크로 재사용해 걸러낸다
    (`obstacle_mask`) — 새 인프라 없이 기존 파이프라인 산출물을 재활용.
- **검증**: 실제 Gazebo 렌더(track_ne_entry_1 스폰 후 캡처)로 HSV 범위를 캘리브레이션(그림자
  진 면도 색상/채도는 유지되고 명도만 낮아짐을 확인). 합성 이미지로 스트레스 테스트: (1) 무관한
  다른 차선이 화면에 같이 보여도 로봇과 안 이어져 있으면 무시함, (2) 트랙에 바로 맞닿아 겹치는
  가짜 오브젝트가 있을 때 마스킹 없이는 offset이 0.20(완전히 틀림)+confidence 1.0(거짓 확신)로
  나오는 반면, obstacle_boxes로 마스킹하면 offset≈0(정답)+confidence 0.46(더 정직한 값)으로
  정상화됨을 확인.
- **미해결**: ROS 2로 넘길 실제 출력 형식(토픽/메시지 타입)과 라이브 노드 배선은 프로젝트
  전체의 ROS 2 인터페이스가 아직 미정(ADR-005)이라 이번엔 순수 인식 함수까지만 구현. 실제
  Signal-Simulation 시뮬레이션과 붙여서 라이브로 검증하는 것도 아직 안 함(합성 이미지 + 정적
  Gazebo 캡처로만 검증).
